# Minecraft 整合包更新器 — 第一版需求文档

**文档版本：** PRD v0.1  
**阶段：** MVP（第一版）  
**目标：** 为后续架构设计、任务拆分及 Coding Agent 实现提供需求基线。

---

## 1. 项目概述

### 1.1 项目背景

当前 Minecraft 整合包由管理员完整打包并分发给玩家。随着 Mod 更新、新增和删除，传统方式需要玩家重新下载整合包或手动替换 JAR 文件。

由于目标用户主要是普通 Minecraft 玩家，不具备软件开发或命令行使用经验，因此需要开发一个简单、现代化的图形界面更新器。

考虑到自行托管大量 Mod 会增加服务器带宽成本，决定采用**服务端管理版本与更新计划、客户端直接从第三方 CDN 下载文件**的架构。

### 1.2 核心目标

1. 玩家通过图形界面完成整合包的检查与更新，不需要手动操作文件。
2. 管理员通过 Web 管理后台维护 Mod 和整合包版本。
3. 服务端根据玩家当前版本计算新增、替换、删除操作。
4. 优先使用 Modrinth 官方 CDN，降低自建服务器带宽压力。
5. 客户端下载全部所需文件并完成哈希校验后，再执行更新。
6. 更新完成后，玩家可以直接打开整合包自带的 HMCL/PCL2 启动器。

### 1.3 目标用户

**普通玩家：** 仅需打开更新程序，检查并安装更新，然后启动游戏。

**管理员：** 通过网页维护 Mod、下载源和整合包版本，发布更新。

第一版优先支持 Windows 10/11 x64。

## 2. 技术选型

| 模块 | 技术方案 |
|---|---|
| 客户端桌面框架 | Tauri 2 |
| 客户端 UI | Vue 3 + TypeScript + Vite |
| 客户端样式 | Tailwind CSS + 自定义组件 |
| 客户端更新核心 | Rust + Tokio + reqwest |
| 服务端 | Rust + Axum |
| 数据库 | SQLite |
| Web 管理端 | Arco Design Pro Vue |
| Mod 元数据 | Modrinth API v2 |
| 首选下载源 | Modrinth CDN |
| 备用下载源 | GitHub Releases / 自定义 HTTPS |
| 文件校验 | SHA-512 |
| 服务端入口 | Nginx + HTTPS |

Rust 服务端与客户端可以使用 Workspace 共享公共数据结构和 API 类型。

## 3. 核心系统架构

系统由三个独立部分组成：

### 3.1 Rust 服务端

负责：

- 维护整合包及 Mod 信息。
- 维护 Mod 版本与文件下载链接。
- 保存每个正式发布版本的完整 Mod 文件清单。
- 接收客户端当前整合包版本。
- 计算当前版本到最新版本的最终更新计划。
- 向客户端返回新增、替换、删除操作。
- 为 Web 管理端提供管理 API。

服务端**不负责转发 Mod 文件下载流量**。

### 3.2 Web 管理端

负责：

- 搜索、添加和移除 Mod。
- 通过 Modrinth API 获取 Mod 版本和下载链接。
- 手动添加其他下载来源。
- 创建整合包版本草稿。
- 配置版本更新内容。
- 发布正式版本。
- 查看历史发布记录。

### 3.3 Rust 玩家客户端

负责：

- 根据预设配置定位整合包实例。
- 读取本地已安装版本。
- 向服务端请求更新计划。
- 展示更新信息与下载进度。
- 并发下载新增、替换所需的 Mod。
- 校验下载文件哈希。
- 统一执行新增、替换和删除操作。
- 保存本地版本信息。
- 打开整合包自带的游戏启动器。

客户端不负责比较历史版本快照，更新决策由服务端完成。

## 4. 整合包版本管理

### 4.1 版本定义

每个发布版本需要保存：

| 字段 | 说明 |
|---|---|
| Release ID | 内部唯一版本标识 |
| Version | 展示版本号，例如 1.2.0 |
| Minecraft Version | 对应游戏版本 |
| Mod Loader | NeoForge / Forge / Fabric |
| Changelog | 更新说明 |
| Published At | 发布时间 |
| Mod Files | 当前版本完整的受管理文件清单 |

正式发布版本的文件清单视为不可变快照。

### 4.2 版本更新方式

管理员创建新版本时，默认从当前正式版本复制 Mod 清单，并在此基础上调整。

支持三种更新操作：

| 操作 | 定义 |
|---|---|
| ADD | 新增一个 Mod 文件 |
| REPLACE | 将现有 Mod 文件替换为指定版本 |
| REMOVE | 删除不再需要的 Mod 文件 |

### 4.3 跨版本更新

服务端必须能够处理玩家跳过多个版本的情况。

例如：

- 玩家本地版本：1.0.0
- 服务端最新版本：1.3.0

服务端直接比较两个发布版本的完整快照，计算最终操作，无须让客户端依次执行 1.1.0、1.2.0 的更新记录。

差异计算以 Mod 的内部唯一 ID 为依据。

旧版本不存在、新版本存在，则新增；旧版本存在、新版本不存在，则删除；两版均存在但目标路径或哈希不同，则替换；完全一致则不返回操作。

## 5. Modrinth 下载源管理

### 5.1 来源优先级

第一版支持以下下载来源：

| 优先级 | 来源 |
|---|---|
| P0 | Modrinth CDN |
| P1 | GitHub Releases |
| P2 | 管理员指定的合法 HTTPS 直链 |

如果 Modrinth 存在准确的目标 Mod 文件，优先使用 Modrinth。

如果 Modrinth 没有对应 Mod，或者没有所需的准确文件版本，管理员可以手动指定其他下载链接。

### 5.2 Modrinth API

服务端集成以下接口：

| 接口 | 用途 |
|---|---|
| GET /search | 搜索 Mod |
| GET /project/{id} | 查询 Mod 信息 |
| GET /project/{id}/version | 查询版本列表 |
| GET /version/{id} | 获取具体版本的文件信息 |
| POST /version_files | 批量通过文件哈希识别版本 |

管理员选择 Modrinth 的某个 Mod 版本后，服务端需要保存：

- Project ID
- Version ID
- 文件名
- 文件大小
- SHA-512
- 官方 CDN 下载 URL

下载链接必须使用 Modrinth API 返回的实际文件地址，不自行拼接 CDN URL。

### 5.3 手动添加下载源

管理员可以填写：

- Mod 名称
- Mod 版本
- 目标文件名
- 下载 URL
- SHA-512
- 文件大小（可选）

文件下载使用 HTTPS。

如果同一个文件配置多个下载来源，所有来源必须对应完全一致的 SHA-512。

### 5.4 API 调用规则

Modrinth API 仅由服务端集成。

玩家客户端不直接调用 Modrinth 搜索或版本查询接口，只使用服务端返回的文件直链。

服务端需要设置可识别的 User-Agent，并对 API 限流响应进行基本处理。不需要在第一版开发复杂的限流管理系统。

## 6. Web 管理端需求

管理端基于 Arco Design Pro Vue 构建。

### 6.1 页面结构

**登录页面**

第一版仅支持单管理员，不需要复杂的用户、角色和权限体系。

**整合包概览**

展示当前正式版本、受管理 Mod 总数、最近发布时间和历史版本。

**Mod 管理页面**

支持按关键词搜索 Modrinth 项目，按 Minecraft 版本与 Mod Loader 筛选，选择具体版本及可下载文件。

也支持手动录入 Mod 与下载源。

**版本发布页面**

管理员可以：

1. 从当前正式版创建新版本草稿。
2. 新增、删除或修改 Mod 的版本。
3. 预览变更内容。
4. 编辑版本号与更新说明。
5. 发布正式版本。

**发布历史页面**

查看已发布的版本及每个版本的新增、替换、删除记录。

### 6.2 发布前检查

仅执行基础检查：

- 版本号不能重复。
- Mod 目标路径不能冲突。
- 新增、替换的文件必须存在下载 URL。
- 必须具有有效格式的 SHA-512。
- 不允许存在非法目标文件路径。

发布后，服务端更新当前正式版本指针，客户端下次请求即可获得对应的更新计划。

## 7. 玩家客户端需求

### 7.1 分发和目录定位

整合包由管理员完整打包，更新器与游戏启动器一起分发。

示意目录：

MyModpack/

- Start.exe：统一入口，Tauri 更新器
- HMCL.exe：游戏启动器
- .minecraft/：游戏实例文件
- .updater/config.json：本地配置
- .updater/state.json：已安装版本
- .updater/staging/：临时下载文件

配置文件至少保存：

| 字段 | 说明 |
|---|---|
| pack_id | 整合包标识 |
| server_url | 更新服务器地址 |
| game_dir | 游戏实例相对路径 |
| launcher_path | 启动器相对路径 |

实际 Mod 目录可能位于 `.minecraft/mods/`，也可能位于某个版本隔离实例目录下，应以配置为准。

所有路径以整合包根目录为参照，不使用绝对安装路径。

第一版不扫描硬盘寻找游戏实例，不依赖 HMCL/PCL2 的启动钩子。

### 7.2 客户端 UI

设计要求：

- 现代、简洁、流畅。
- Windows 桌面程序体验。
- 圆角、柔和动画、清晰的下载状态。
- 主要操作按钮突出。
- 不采用复杂后台管理系统式布局。

主要界面：

**首页**

展示整合包名称、本地版本、最新版本、更新说明和操作按钮。

**更新确认**

展示新增、替换、删除的 Mod 数量和变更内容，允许玩家开始更新。

**下载进度**

展示总体进度、当前下载文件、已完成数量、下载速度和失败状态。

**完成页面**

提示更新成功，并提供打开 HMCL/PCL2 的按钮。

**错误页面**

显示网络错误、下载失败、哈希不一致或文件操作失败，并提供简单、易理解的重试指引。

下载和文件处理全部放在 Rust 异步任务中，前端只负责展示。进度更新需要限制刷新频率，避免不必要的频繁渲染。

### 7.3 更新流程

客户端启动后按以下顺序执行：

1. 读取本地配置与已安装整合包版本。
2. 请求服务端更新计划。
3. 如果没有更新，允许直接打开游戏启动器。
4. 如果存在更新，展示目标版本和变更摘要。
5. 玩家确认后，开始并发下载全部新增和替换所需文件。
6. 文件下载到临时目录，不直接写入 `mods`。
7. 所有文件下载成功后计算 SHA-512，并与预期哈希比较。
8. 全部校验成功后执行替换、删除、新增操作。
9. 所有文件操作完成后更新本地版本号。
10. 显示更新完成，允许打开游戏启动器。

**关键要求：全部新文件下载完成并且哈希校验通过之前，不能修改原有游戏目录。**

### 7.4 下载要求

- 默认最多 4 个 Mod 并发下载。
- 不需要对单个文件进行多线程分段下载。
- 下载失败可进行最多 2～3 次简单重试。
- 下载地址可以按管理员设置的优先级切换。
- 只对下载的新文件执行 SHA-512 校验。
- 不需要扫描整个游戏目录或重新校验全部旧 Mod。

### 7.5 错误处理

下载或校验失败时，停止更新，不执行文件替换或删除，向玩家提供重试入口。

文件安装失败时，不更新本地发布版本记录，不提示成功，也不继续打开游戏启动器。

第一版不实现复杂自动回滚机制。再次运行更新程序时，可以重新请求相同的更新计划并重试。

若仅检查更新阶段网络不可用，且没有进行文件修改，可允许用户选择离线打开已有启动器，并提示无法确认是否为最新版本。

## 8. 更新 API

### 8.1 获取更新计划

`POST /api/v1/packs/{pack_id}/update-plan`

请求信息：

| 字段 | 说明 |
|---|---|
| installed_release_id | 当前本地整合包版本 ID |
| client_version | 更新器程序版本 |

响应信息：

| 字段 | 说明 |
|---|---|
| target_release_id | 目标整合包版本 ID |
| target_version | 目标展示版本 |
| changelog | 版本更新说明 |
| operations | 最终更新操作列表 |

### 8.2 更新操作结构

每个操作具有 `action` 和 `mod_id`。

**ADD：** 返回目标路径、文件大小、SHA-512 与下载源列表。

**REPLACE：** 额外包含旧文件路径，以及目标文件的完整下载信息。

**REMOVE：** 返回需要删除的原文件路径，不需要下载信息。

路径统一表示为相对于游戏实例目录的路径，第一版仅处理 `mods/` 下的 JAR 文件。

服务端应拒绝未知整合包版本，并返回清晰的错误状态，而不是自行猜测客户端实际拥有的文件。

### 8.3 无更新情况

如果本地版本已经是最新版本，返回空操作列表：

`operations: []`

客户端直接进入就绪状态。

## 9. 服务端数据模型

| 实体 | 主要内容 |
|---|---|
| pack | 整合包 ID、名称、MC 版本、Loader、当前发布版本 |
| mod | 内部 Mod ID、名称、Modrinth Project ID |
| artifact | 对应 Mod 的具体文件版本、文件名、大小、SHA-512 |
| download_source | Artifact ID、下载 URL、来源、优先级 |
| release | 发布版本 ID、整合包 ID、版本号、说明、发布时间 |
| release_item | 发布版本与 Mod 文件之间的关联及目标路径 |
| admin | 管理员认证信息 |

数据模型允许按照实际实现习惯适当合并，但需要保留完整历史版本快照与明确的文件哈希信息。

## 10. 第一版非功能性需求

### 10.1 基础性能

客户端网络及文件操作不能阻塞 UI。

支持多文件并发下载，并提供持续更新的进度反馈。

### 10.2 基础安全

- 管理端 API 必须要求管理员身份认证。
- 更新服务使用 HTTPS。
- 下载使用 HTTPS。
- 文件路径必须限制在整合包允许的 Mod 目录内。
- 拒绝路径穿越和非法绝对路径。
- 不允许随意删除未纳入管理的玩家文件。
- 文件哈希不匹配则禁止安装该文件。

### 10.3 第一版不实现

- 自动回滚及完整事务日志。
- 复杂 Mod 依赖求解。
- 自动更新 Minecraft 或 ModLoader。
- 客户端更新器自更新。
- 资源包、配置文件、存档同步。
- CDN 分段下载与测速调度。
- 数字签名和高级供应链安全体系。
- 多租户、多管理员权限系统。
- 完整游戏启动器与账号认证功能。

## 11. 验收标准

| 测试场景 | 预期结果 |
|---|---|
| 玩家已使用最新版 | 不下载任何文件，允许启动 |
| 发布新增 Mod | 客户端下载并加入目标目录 |
| 发布替换 Mod | 客户端安装新版本并移除旧版本 |
| 发布删除 Mod | 客户端删除指定受管理文件 |
| 玩家跨多个版本更新 | 直接按最终差异更新到最新版本 |
| 部分 Mod 下载失败 | 不修改原有游戏文件 |
| 下载文件哈希不一致 | 拒绝执行更新 |
| 使用自定义 HTTPS 下载源 | 正确下载并完成校验 |
| 玩家自行添加额外 Mod | 更新后该文件保留 |
| 整合包移动到其他磁盘 | 根据相对路径正常定位游戏与启动器 |
| 更新时文件操作失败 | 不记录成功版本、不继续启动 |
| 更新全部完成 | 保存最新版本号，并可打开启动器 |

## 12. 开发实施顺序

**Phase 1：服务端核心**

完成数据库模型、Modrinth API 接入、版本快照、增量操作计算及更新计划 API。

**Phase 2：Rust 更新核心**

完成实例定位、版本读取、下载、哈希校验、文件操作、本地状态更新和启动器打开功能。

**Phase 3：可视化界面**

完成 Arco Design Pro Vue 管理后台和 Tauri 2 客户端界面，接入真实 API。

**Phase 4：端到端测试**

使用真实 Minecraft 整合包验证新增、替换、删除、跨版本更新、网络失败与文件操作失败等场景。

---

## 13. 核心设计原则

1. **服务端决定更新什么，客户端负责执行。**
2. 服务端保存完整历史快照，客户端只接收最终操作。
3. Modrinth 优先，其他来源作为补充。
4. 所有下载与基本哈希校验完成后，才修改游戏目录。
5. 更新器是整合包的统一入口，不依赖其他启动器的更新钩子。
6. 面向普通玩家设计界面，避免命令行和复杂配置。
7. 第一版以最小可用闭环为目标，避免提前开发复杂基础设施。

本需求文档作为 MVP 开发基线，后续技术实现可以优化内部代码结构，但不应擅自增加明显超出第一版范围的功能。
