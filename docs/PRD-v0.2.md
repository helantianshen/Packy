# Minecraft 整合包更新器 — 第一版需求文档

**文档版本：** PRD v0.2（审查稿）  
**更新日期：** 2026-10-15  
**状态：** 历史业务基线；2026-10-18 新栈与单管理员简化以 docs/specs/go-electron-redevelopment.md、docs/contracts 为准，本文注册/RBAC/Tauri 要求已撤销
**阶段：** MVP（第一版）  
**目标：** 为后续架构设计、任务拆分及 Coding Agent 实现提供需求基线。

---

## 1. 项目概述

### 1.1 项目背景

当前 Minecraft 整合包由管理员完整打包并分发给玩家。随着 Mod 更新、新增和删除，传统方式需要玩家重新下载整合包或手动替换 JAR 文件。

由于目标用户主要是普通 Minecraft 玩家，不具备软件开发或命令行使用经验，因此需要开发一个简单、现代化的图形界面更新器。

考虑到自行托管大量 Mod 会增加服务器带宽成本，决定采用**服务端管理版本与更新计划、客户端按已取得记录从指定下载源下载文件**的架构。

### 1.2 核心目标

1. 玩家通过图形界面完成整合包的检查与更新，不需要手动操作文件。
2. 管理员通过 Web 管理后台维护 Mod 和整合包版本。
3. 服务端根据玩家当前版本计算新增、替换、删除操作。
4. 优先使用 Modrinth 官方 CDN，降低自建服务器带宽压力。
5. 客户端下载全部所需文件并完成哈希校验后，再执行更新。
6. 更新完成后，玩家可以直接打开整合包自带的 HMCL/PCL2 启动器。

### 1.3 目标用户

**普通玩家：** 仅需打开更新程序，检查并安装更新，然后启动游戏。

**管理员：** 通过网页维护 Mod、下载源和整合包版本，发布更新。

第一版优先支持 Windows 10/11 x64。

## 2. 技术选型

| 模块 | 技术方案 |
|---|---|
| 客户端桌面框架 | Tauri 2；精确版本由 Cargo.lock 固定 |
| 客户端 UI | Vue 3 + TypeScript + Vite |
| 客户端样式 | 共享 CSS 主题 + 自定义组件 |
| 客户端更新核心 | Rust；网络、并发、SHA-512 和文件操作在独立核心 crate 实现 |
| 服务端 | Rust；HTTP 路由与数据库访问方案见架构审查稿 |
| 数据库 | SQLite |
| Web 管理端 | Arco Design Vue |
| Mod 元数据 | Modrinth API v2 |
| 首选下载源 | Modrinth CDN |
| 下载源范围 | Modrinth / CurseForge / GitHub / Rust 服务端；字典管理 |
| 后台认证 | JWT 登录；管理员配置注册开关，实时生效 |
| 文件校验 | SHA-512 |
| 服务端入口 | Nginx + HTTPS |

服务端与客户端核心均使用 Rust；建议单仓库、Cargo workspace，共享协议类型和必要的校验逻辑。客户端核心不依赖 Tauri，Vue 3 通过 Tauri commands 与进度事件调用核心，不启动额外的本地 HTTP API。

前端由 AI 辅助实现，用户重点关注 Rust 后端与核心逻辑；UI 的实际视觉和交互体验仍需人工验收。具体模块边界与待决策项见 [架构审查稿](ARCHITECTURE.md)，阶段验收见 [开发计划](DEVELOPMENT-PLAN.md)。

## 3. 核心系统架构

系统由三个独立部分组成：

### 3.1 Rust 服务端

负责：

- 维护整合包及 Mod 信息。
- 维护 Mod 版本与文件下载链接。
- 保存每个正式发布版本的完整 Mod 文件清单。
- 接收客户端当前整合包版本。
- 计算当前版本到最新版本的最终更新计划。
- 向客户端返回新增、替换、删除操作。
- 为 Web 管理端提供管理 API。

第三方来源文件由客户端直连下载；Rust 服务端来源由本服务提供已托管文件下载。客户端拿到完整更新记录、SHA-512 和下载链接后独立执行，不需要服务端继续调度或刷新计划。使用 Rust 服务端来源时仍有文件传输流量。

### 3.2 Web 管理端

负责：

- 搜索、添加和移除 Mod。
- 通过 Modrinth API 获取 Mod 版本和下载链接。
- 手动添加其他下载来源。
- 创建整合包版本草稿。
- 配置版本更新内容。
- 发布正式版本。
- 查看历史发布记录。

### 3.3 Rust 玩家客户端

负责：

- 根据预设配置定位整合包实例。
- 读取本地已安装版本。
- 向服务端请求更新计划。
- 展示更新信息与下载进度。
- 并发下载新增、替换所需的 Mod。
- 校验下载文件哈希。
- 统一执行新增、替换和删除操作。
- 保存本地版本信息。
- 打开整合包自带的游戏启动器。

客户端不负责比较历史版本快照，更新决策由服务端完成。

## 4. 整合包版本管理

### 4.1 版本定义

每个发布版本需要保存：

| 字段 | 说明 |
|---|---|
| Release ID | 内部唯一版本标识 |
| Version | 展示版本号，例如 1.2.0 |
| Minecraft Version | 对应游戏版本 |
| Mod Loader | NeoForge / Forge / Fabric |
| Changelog | 更新说明 |
| Published At | 发布时间 |
| Mod Files | 当前版本完整的受管理文件清单 |

正式发布版本的文件清单视为不可变快照。

### 4.2 版本更新方式

管理员创建新版本时，默认从当前正式版本复制 Mod 清单，并在此基础上调整。

支持三种更新操作：

| 操作 | 定义 |
|---|---|
| ADD | 新增一个 Mod 文件 |
| REPLACE | 将现有 Mod 文件替换为指定版本 |
| REMOVE | 删除不再需要的 Mod 文件 |

### 4.3 跨版本更新

服务端必须能够处理玩家跳过多个版本的情况。

例如：

- 玩家本地版本：1.0.0
- 服务端最新版本：1.3.0

服务端直接比较两个发布版本的完整快照，计算最终操作，无须让客户端依次执行 1.1.0、1.2.0 的更新记录。

业务 modid 唯一，Mod 名称允许重复，不以名称匹配或合并 Mod。内部稳定记录 ID 与业务 modid、各来源 Project ID 分离；修改 modid 时编辑原记录，保留内部 ID 与历史关联，并检查新 modid 未被占用。历史快照保存当时的 modid 和文件信息，不能被当前记录修改覆盖。跨版本按稳定记录 ID 关联，使用快照中的旧路径和新文件生成操作。

旧版本不存在、新版本存在，则新增；旧版本存在、新版本不存在，则删除；两版均存在但目标路径或哈希不同，则替换；完全一致则不返回操作。

## 5. 下载源与字典管理

### 5.1 下载源范围

第一版仅支持以下四类来源，不增加任意自定义来源类别：

| 字典编码 | 来源 | 客户端使用方式 |
|---|---|---|
| modrinth | Modrinth | 已解析的文件直链 |
| curseforge | CurseForge | 已解析且可供客户端直接下载的文件链接 |
| github | GitHub Releases | 指定发布资产的下载链接 |
| server | Rust 服务端 | 本服务已托管文件的下载链接 |

下载源类型、显示名称、启用状态和默认排序通过字典管理；具体 Artifact 的 URL、文件大小、哈希和来源排序另行保存。字典不保存文件内容或 API 密钥，不承担动态代码插件功能。优先使用 Modrinth；其他来源顺序按字典及文件配置确定。

字典变更影响后续维护和计划生成，不修改客户端已经取得的记录。禁用不等于删除已发布文件；引用中的字典编码保持稳定，不物理删除或改作另一类来源。

### 5.2 Modrinth 元数据

沿用 GET /search、GET /project/{id}、GET /project/{id}/version、GET /version/{id}、POST /version_files。

服务端保存 Project ID、Version ID、文件名、大小、SHA-512 和 API 返回的实际文件 URL，不自行拼接 CDN 地址。Modrinth 元数据 API 仅由服务端调用，设置可识别 User-Agent，处理超时和基本限流。

### 5.3 文件录入与链接准备

管理员为文件保存 Mod 名称、业务 modid、Mod 版本、目标文件名、来源类型、下载 URL、SHA-512、可选文件大小。Modrinth 可通过已有元数据流程录入；CurseForge/GitHub 第一版可录入指定文件链接，不自动扩展为完整平台搜索与同步系统。

所有来源最终都必须产生同一种完整文件记录。相同 Artifact 的多个来源必须对应相同 SHA-512。链接支持 HTTP/HTTPS，HTTPS 重定向不得降级为 HTTP，不能向客户端下发管理员 JWT 或第三方 API 密钥。普通玩家下载不要求登录后台。

CurseForge 获取文件 URL 的 API 需要 API Key；其文件哈希枚举列出 SHA-1/MD5。若需要 API 解析，应在服务端准备链接；SHA-512 由管理员针对实际文件提供，或在受控导入时计算，不能把其他哈希冒充 SHA-512。没有可用链接或 SHA-512 的文件不得发布。官方依据见架构文档。

### 5.4 Rust 服务端下载源

Rust 服务端提供已录入文件的 HTTP/HTTPS 下载地址；推荐由后台上传 JAR，服务端计算 SHA-512 并按不可变文件标识保存。文件目录与应用配置、SQLite 和管理端静态资源隔离，下载 API 按文件标识寻址，不接受任意磁盘路径。

本来源提供文件服务，不代理所有第三方来源，也不参与客户端更新状态调度。文件录入/上传仅管理员可用，已发布链接应保持可下载；新增、禁用字典项不能改写已发出的 URL 内容。

## 6. Web 管理端需求

管理端基于 Arco Design Vue 构建。

### 6.1 页面结构

**登录页面**

管理员使用账号密码登录并获取 JWT，后端校验 JWT 后允许相应管理操作。提供注册入口，但能否注册由系统管理的 registration_enabled 开关决定。系统采用 RBAC，第一版仅有超管和普通用户两种角色。注册只能创建普通用户，不接受客户端指定管理员角色或权限。

**整合包概览**

展示当前正式版本、受管理 Mod 总数、最近发布时间和历史版本。

**Mod 管理页面**

支持按关键词搜索 Modrinth 项目，按 Minecraft 版本与 Mod Loader 筛选，选择具体版本及可下载文件。

也支持手动录入 Mod 与下载源。

**版本发布页面**

管理员可以：

1. 从当前正式版创建新版本草稿。
2. 新增、删除或修改 Mod 的版本。
3. 预览变更内容。
4. 编辑版本号与更新说明。
5. 发布正式版本。

**发布历史页面**

查看已发布的版本及每个版本的新增、替换、删除记录。

**系统管理页面**

- 管理下载源字典：四类来源的名称、启用状态和排序。
- 配置 registration_enabled：是否开放注册，保存后立即影响后端注册接口，不需要重启。
- 超管拥有用户管理与权限管理功能；普通用户仅能执行明确授予该角色的操作，默认不具有管理写权限。
- 通过 SQL 初始化两种角色和一个超管账号；初始化使用已生成的密码哈希，部署者负责妥善配置凭据及是否关闭注册。
- 前端可读取开关展示入口，但即使旧页面仍显示注册按钮，后端也必须按当前值拒绝已关闭的注册。
- 开关仅控制新注册，不影响现有账号登录。JWT 签发不代替注册开关检查。

### 6.2 发布前检查

仅执行基础检查：

- 版本号不能重复。
- Mod 目标路径不能冲突。
- 新增、替换的文件必须存在下载 URL。
- 必须具有有效格式的 SHA-512。
- 不允许存在非法目标文件路径。

发布后，服务端更新当前正式版本指针，客户端下次请求即可获得对应的更新计划。

## 7. 玩家客户端需求

### 7.1 分发和目录定位

整合包由管理员完整打包，更新器与游戏启动器一起分发。

示意目录：

MyModpack/

- Start.exe：统一入口，Tauri 更新器
- HMCL.exe：游戏启动器
- .minecraft/：游戏实例文件
- config/client.<platform>.yaml：管理员在项目中维护的构建配置，通过 include_str! 嵌入程序，不随整包分发；旁置 .updater/config.json 不生效
- .updater/state.json：已安装版本
- .updater/staging/：临时下载文件

项目构建配置至少保存：

| 字段 | 说明 |
|---|---|
| pack_id | 当前服务器整合包标识 |
| pack_name | 专用客户端名称，默认蒹葭服务器整合包，不随更新清单变化 |
| server_url | 组包时填写的完整 HTTP/HTTPS 更新服务器地址 |
| game_dir | 游戏实例相对路径 |
| launcher_path | 启动器相对路径 |

客户端是蒹葭服务器专用更新器，不提供玩家切换整合包的入口。后台运行用户偏好单独保存在 `.updater/preferences.json` 的 `background_enabled` 字段，默认 true；不覆盖管理员的组包配置。

实际 Mod 目录可能位于 `.minecraft/mods/`，也可能位于某个版本隔离实例目录下，应以配置为准。

所有路径以整合包根目录为参照，不使用绝对安装路径。

第一版不扫描硬盘寻找游戏实例，不依赖 HMCL/PCL2 的启动钩子。更新器直接随整合包分发可执行程序，不制作安装包，也不提供自更新。

### 7.2 客户端 UI

设计要求：

- 现代、简洁、流畅。
- Windows 桌面程序体验。
- 圆角、柔和动画、清晰的下载状态。
- 主要操作按钮突出。
- 不采用复杂后台管理系统式布局。

主要界面：

**首页**

展示整合包名称、本地版本、最新版本、更新说明和操作按钮。

**更新确认**

展示新增、替换、删除的 Mod 数量和变更内容，允许玩家开始更新。

**下载进度**

展示总体进度、当前下载文件、已完成数量、下载速度和失败状态。

**完成页面**

提示更新成功，并提供打开 HMCL/PCL2 的按钮。更新和本地版本保存完成后发送系统通知；通知不可用时保留窗口中的完成提示。

**错误页面**

显示网络错误、下载失败、哈希不一致或文件操作失败，并提供简单、易理解的重试指引。

下载和文件处理全部放在 Rust 后台任务中，前端负责展示与提交用户操作。任务是否成功、能否安装和启动由 Rust 核心判断。进度更新需要限制刷新频率，避免不必要的频繁渲染。

### 7.3 系统托盘与后台更新

后台运行开关默认开启并保存在当前整合包中，保存成功后立即生效。开启时关闭窗口隐藏至系统托盘，后台下载和安装继续执行；关闭时关闭窗口按安全退出规则处理。托盘提供打开主界面和退出入口；安装与保存版本期间禁止退出，下载阶段退出须取消并保存原任务。更新成功后发送系统通知，点击通知的可用行为以平台支持为准，托盘始终可重新打开窗口。通知权限或发送失败不改变实际安装结果。

### 7.4 更新流程

客户端启动后按以下顺序执行：

1. 读取本地配置与已安装整合包版本。
2. 请求服务端更新计划。
3. 如果没有更新，允许直接打开游戏启动器。
4. 如果存在更新，展示目标版本和变更摘要。
5. 玩家确认后，开始并发下载全部新增和替换所需文件。
6. 文件下载到临时目录，不直接写入 `mods`。
7. 所有文件下载成功后计算 SHA-512，并与预期哈希比较。
8. 全部校验成功后执行替换、删除、新增操作。
9. 所有文件操作完成后更新本地版本号。
10. 显示更新完成，允许打开游戏启动器。

**关键要求：全部新文件下载完成并且哈希校验通过之前，不能修改原有游戏目录。**

仅操作本次更新记录列出的路径；名单外的 Mod 不扫描、不校验、不删除、不整理，不识别玩家自加 Mod 的来源或依赖。替换涉及的旧路径也必须在记录中明确列出。同名同路径以记录为准处理，不增加玩家 Mod 冲突管理系统；两个不同文件不可能同时占用同一路径。

### 7.5 下载要求

- 默认最多 4 个 Mod 并发下载。
- 不需要对单个文件进行多线程分段下载。
- 下载失败可进行最多 2～3 次简单重试。
- 下载地址可以按管理员设置的优先级切换。
- 只对下载的新文件执行 SHA-512 校验。
- 不需要扫描整个游戏目录或重新校验全部旧 Mod。

### 7.6 错误处理

下载或校验失败时，停止更新，不执行文件替换或删除，向玩家提供重试入口。

文件安装失败时，不更新本地发布版本记录，不提示成功，也不继续打开游戏启动器。

第一版不实现复杂自动回滚机制、服务端任务调度或更新中途的新版协调。客户端按已取得的记录重试；该任务不重新获取计划，不查询“最新版本是否变化”。本地可保存任务记录支持重启后继续原任务，文件失败不写成功版本；无须服务端保存任务进度。

若仅检查更新阶段网络不可用，且没有进行文件修改，可允许用户选择离线打开已有启动器，并提示无法确认是否为最新版本。

## 8. 更新 API

### 8.1 获取更新计划

`POST /api/v1/packs/{pack_id}/update-plan`

请求信息：

| 字段 | 说明 |
|---|---|
| installed_release_id | 当前本地整合包版本 ID |
| client_version | 更新器程序版本 |

响应信息：

| 字段 | 说明 |
|---|---|
| target_release_id | 目标整合包版本 ID |
| target_version | 目标展示版本 |
| changelog | 版本更新说明 |
| operations | 最终更新操作列表 |

### 8.2 更新操作结构

每个操作具有 `action` 和 `mod_id`。这里 `mod_id` 表示稳定的内部记录 ID；业务 modid 使用独立字段，避免改业务 modid 后失去旧文件关联。

**ADD：** 返回目标路径、文件大小、SHA-512 与下载源列表。

**REPLACE：** 额外包含旧文件路径，以及目标文件的完整下载信息。

**REMOVE：** 返回需要删除的原文件路径，不需要下载信息。

路径统一表示为相对于游戏实例目录的路径，第一版仅处理 `mods/` 下的 JAR 文件。

服务端应拒绝未知整合包版本，并返回清晰的错误状态，而不是自行猜测客户端实际拥有的文件。

### 8.3 无更新情况

如果本地版本已经是最新版本，返回空操作列表：

`operations: []`

本地已是最新版本且无未完成任务时进入就绪状态。本版不设计“不同发布 ID 但 operations 为空”的专门流程、状态推进或验收用例。

## 9. 服务端数据模型

| 实体 | 主要内容 |
|---|---|
| pack | 整合包 ID、名称、MC 版本、Loader、当前发布版本 |
| mod | 稳定内部 ID、可重复的 Mod 名称、唯一业务 modid、各来源 Project ID |
| artifact | 对应 Mod 的具体文件版本、文件名、大小、SHA-512 |
| download_source_type | 四类来源字典：编码、名称、启用状态、排序 |
| download_source | Artifact ID、下载 URL、来源字典编码、优先级 |
| release | 发布版本 ID、整合包 ID、版本号、说明、发布时间 |
| release_item | 发布版本与 Mod 文件之间的关联及目标路径 |
| account | 登录账号、密码哈希、账号状态 |
| role / permission | 超管、普通用户角色，以及可授权的权限项 |
| account_role / role_permission | 用户角色、角色权限关联；注册固定普通用户 |
| system_setting | registration_enabled 等系统设置 |
| hosted_file | Rust 服务端托管文件标识、存储位置、大小和 SHA-512 |

数据模型允许按照实际实现习惯适当合并，但需要保留完整历史版本快照与明确的文件哈希信息。

## 10. 第一版非功能性需求

### 10.1 基础性能

客户端网络及文件操作不能阻塞 UI。

支持多文件并发下载，并提供持续更新的进度反馈。

### 10.2 基础安全

- 管理端 API 必须要求管理员身份认证。
- 更新服务支持 HTTP/HTTPS，公网部署使用 Nginx 终止 HTTPS。
- 下载支持 HTTP/HTTPS，HTTPS 重定向不得降级为 HTTP。
- 文件路径必须限制在整合包允许的 Mod 目录内。
- 拒绝路径穿越和非法绝对路径。
- 不允许随意删除未纳入管理的玩家文件。
- 文件哈希不匹配则禁止安装该文件。

### 10.3 第一版不实现

- 自动回滚及完整事务日志。
- 复杂 Mod 依赖求解。
- 自动更新 Minecraft 或 ModLoader。
- 客户端更新器自更新。
- 资源包、配置文件、存档同步。
- CDN 分段下载与测速调度。
- 数字签名和高级供应链安全体系。
- 多租户及超出两种初始角色的复杂组织/数据权限体系；本版实现基础 RBAC、用户管理与权限管理。
- 完整游戏启动器与账号认证功能。

## 11. 验收标准

| 测试场景 | 预期结果 |
|---|---|
| 玩家已使用最新版 | 不下载任何文件，允许启动 |
| 发布新增 Mod | 客户端下载并加入目标目录 |
| 发布替换 Mod | 客户端安装新版本并移除旧版本 |
| 发布删除 Mod | 客户端删除指定受管理文件 |
| 玩家跨多个版本更新 | 直接按最终差异更新到最新版本 |
| 部分 Mod 下载失败 | 不修改原有游戏文件 |
| 下载文件哈希不一致 | 拒绝执行更新 |
| 使用四类配置来源之一 | 使用给定链接下载并通过 SHA-512 校验 |
| 玩家自行添加额外 Mod | 更新后该文件保留 |
| 整合包移动到其他磁盘 | 根据相对路径正常定位游戏与启动器 |
| 更新时文件操作失败 | 不记录成功版本、不继续启动 |
| 更新全部完成 | 保存最新版本号，并可打开启动器 |

## 12. 开发实施顺序

**Phase 1：服务端核心**

**Phase 2：Rust 更新核心**

**Phase 3：可视化界面**

**Phase 4：端到端测试**

## 13. 核心设计原则

1. **服务端决定更新什么，客户端负责执行。**
2. 服务端保存完整历史快照，客户端只接收最终操作。
3. 来源限定 Modrinth、CurseForge、GitHub 和 Rust 服务端，由字典管理。
4. 所有下载与基本哈希校验完成后，才修改游戏目录。
5. 更新器是整合包的统一入口，不依赖其他启动器的更新钩子。
6. 面向普通玩家设计界面，避免命令行和复杂配置。
7. 第一版以最小可用闭环为目标，避免提前开发复杂基础设施。

本需求文档作为 MVP 开发基线，后续技术实现可以优化内部代码结构，但不应擅自增加明显超出第一版范围的功能。

## 14. 审查意见落实与剩余语义

### 14.1 用户已确认

- 使用 Tauri 2 + Vue 3，服务端和客户端核心使用 Rust。
- 客户端取得完整记录后自行下载、校验、安装；重试不查询新版，不引入服务端协调。
- 下载源仅 Modrinth、CurseForge、GitHub、Rust 服务端，采用字典管理。
- 仅处理本次记录，玩家添加且不在本次记录里的 Mod 完全不处理；取消独立玩家文件识别和冲突管理方案。
- 不实现不同发布 ID 且空 operations 的额外流程。
- 业务 modid 唯一，Mod 名称可重复；修改 modid 保留原内部记录身份。
- 保留明确的 REMOVE，名单外完全不处理。
- 管理员 JWT 登录，基础 RBAC；SQL 初始化超管与普通用户角色和首个超管账号。
- 注册只能创建普通用户，超管拥有用户管理、权限管理及注册开关配置；开关后端实时生效。
- 保留 Rust 核心与 Tauri 解耦、Cargo workspace、SQLite、完整快照和分阶段开发方向；实现与验证进展见开发计划和验证记录。

### 14.2 已澄清的语义

- 名称不唯一，不承担身份匹配；业务 modid 唯一，修改时对原记录操作。
- ADD、REPLACE、REMOVE 均保留，只操作记录内路径。
- 开放注册不开放超管注册；后台以 RBAC 判断用户实际权限，不能只验证 JWT 是否存在。
- SQL 初始化内置角色和首个超管，重复初始化不覆盖现有密码与权限配置；具体初始化参数在实施阶段定义。
- 本次不再讨论上一稿的 v2、Session、玩家 Mod 冲突管理或空差异版本推进方案。

### 14.3 新增验收

- 客户端取得记录后，更新计划 API 不可用或服务端发布新版，均不影响按原链接执行；若来源就是 Rust 服务端，文件服务本身仍必须可用。
- 四类字典项可管理；调整字典不会修改已经交给客户端的任务。
- JWT 缺失、过期、签名错误均不能访问受保护管理接口。
- 关闭注册后旧网页提交也会被拒绝；重新开启后新请求可注册，无须重启。
- 注册与开关变更并发时按数据库提交顺序判定，不能先通过检查再在关闭后创建账号。
- 名单外文件在更新前后保持不变，不新增全目录 Mod 扫描。

- 重名但不同 modid 可保存；重复 modid 被拒绝；原记录改 modid 后历史快照不变，更新关系仍可追踪。
- SQL 初始化可建立首个超管；注册请求夹带超管角色或权限字段不能提升权限。
- 普通用户不能越权访问用户、权限和系统管理；超管可执行已定义的用户与角色权限管理。

## HTTP/HTTPS 部署与联调补充（2026-10-15）

用户确认客户端支持 HTTP/HTTPS 服务地址和下载链接。Rust 服务端只监听 HTTP，不配置 TLS；自部署由 Nginx 终止 HTTPS 并转发 HTTP。PACKY_PUBLIC_URL 使用客户端实际可访问的 HTTP/HTTPS 外部地址，不能使用内部反代地址生成下载链接。本地联调用 HTTP。HTTPS 链接的重定向不允许降级为 HTTP；初始 HTTP 链接可正常使用。完成客户端和服务端后执行实际联调，检查计划、下载、校验、安装、失败重试与版本落盘，不能仅以单元测试代替。
